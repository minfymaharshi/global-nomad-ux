How Global Nomad is built

Every component, every state, every measurement, for a phone in a flooded street and a desktop in an office. Greys only until a look is agreed — then the values in Greys and Type are the only things that change.

00

How to use this

Pick Desktop or Phone at the top. Type sizes, touch sizes and the notes all follow that choice, because the same component is not the same thing in a warehouse office and on a phone in the rain.

Every component below is live, drawn by the same code as the prototype. If something looks wrong here it is wrong there too.

Do

Change a component here in the same commit you change it in the prototype. The two files are kept in step by hand.

Do not

Add a colour, a typeface or a shadow that is not in this file. If something needs one, add it here first and say why.

Still open: what we call things in each place

A site is a “relief camp” in the Emirates and a “shelter” in the States. That switch is built and working, but the full list of words per place is not settled. See Words.

01

Words

Someone reading a cracked screen in daylight has to understand a button without stopping to think. That rules out most of the language a system naturally grows.

The four rules

  1. Say what will happen. The button says Send request. The message afterwards says Request sent.
  2. No system words. Nothing about allocating, dispatching, validating, scoping or fulfilling.
  3. Numbers before adjectives. “3 of 60 boxes arrived”, not “partially delivered”.
  4. Errors say what to do next. Never “an error occurred”.

Rules for both

  • Numbers that line up in a column use fixed-width figures.
  • No long stretches of capitals — four words at most.
  • Everything must survive 200% zoom and wider letter spacing without breaking.
  • Only two weights: 400 for reading, 650 for headings and labels.
  • Never set a size inline. An inline size cannot be raised by the phone floor, so anything written straight onto an element quietly stays at its desktop size on a phone. Use a class.
  • No exceptions to the floor. Small caps used to sit at 11px on the argument that capitals read larger. They now meet the floor like everything else — an exception is an argument waiting to happen.
Found by the check

Fourteen places sat below the floor, including every status chip, every table heading and the step numbers. Three more were inline sizes that looked right on a desktop and stayed too small on a phone. None of it was visible by eye — it took measuring the drawn page.

05

Icons

Drawn as plain shapes in the page. Nothing downloaded, so they work with no signal and stay sharp at any size. Thick strokes and big forms, because they have to read on a scratched screen in bright sun.

Do

Put a word next to the icon for anything that changes data.

Do not

Use an icon alone, except for close, back and menu — and those still carry a spoken label.

Do

Draw at 20–22px on desktop, 22–24px on a phone, inside a 44px touch area.

Do not

Add fine detail, thin strokes or a second colour. It disappears at size.

Add one by adding a shape to the list. Two lines of code, no file, no build step, no licence to check.

06

Movement

Five movements. Each has a job. Nothing else moves.

NameTimeWhat it is forWhat moves

The four rules

  1. Only fading and moving. Never width, height, padding or type size — those make a cheap phone redo its layout and the animation stutters.
  2. Nothing longer than 320ms. Past that it feels like waiting.
  3. Everything switches off. The system “reduce motion” setting and the Movement control in the prototype both stop all of it.
  4. Movement never delays a task. The button responds first; the animation is decoration on top.
Caught by this rule

The progress bar animated its width, which makes the phone recalculate layout on every frame. It now scales instead. The check fails the build if that comes back.

Waiting

  • Under 400ms: nothing. A flash of a spinner is worse than no spinner.
  • Over 400ms: the button shows a spinner and says what it is doing.
  • A whole screen loading: grey blocks in the shape of the content, never a blank page.

Components

Each one shows what it looks like, every state it can be in, and what a developer needs to know. Where a phone differs from a desktop, both are given.

Side list

.side

How someone moves around. Grouped under headings so a long list stays readable, and foldable to icons when the screen is needed for the work rather than the navigating. The bell and the person's name sit in a block at the bottom, out of the list — you navigate to pages, you glance at alerts.

Width
Open 220px. Folded 60px.
Item
36px tall, icon and label with a 12px gap, padding 6px 10px.
On a phone
There is no side list. It becomes a sheet reached from the header, and the four main pages sit in a bottom bar with 44px targets.
Groups
A heading in small caps, then its items. A hairline between groups, never a heavy rule.
Current page
Boxed: white fill, a 1px edge, and the label goes to 650. Three signals, so it does not depend on one.
Folding
No animation. Animating a width makes the browser redo layout every frame. It snaps, and the movement check enforces that.
Folded labels
Each icon keeps its label for a screen reader and as a hover tooltip. An icon alone is never the only clue.
Unread alerts
An 8px dot at the bell's top right — not a number. At the sizes a bell is drawn, a two-digit count is smaller than the text floor and turns the icon into a smudge. The dot answers the only question a glance asks: is there anything new? The count itself belongs on the Alerts page, where there is room to say what the alerts are.
Dot colour
--solid, the same dark neutral as body text, with a 2px ring in the surface colour so it reads against the icon. Not a warning colour: at wireframe stage nothing may carry meaning by colour alone, and “there is something new” is not the same as “something is wrong”.
Access
A real <nav> with a name. Current item marked aria-current="page". The fold button reports aria-expanded. The dot is aria-hidden; the number still reaches a screen reader through the link's own text — “Alerts, 2 unread”, never “2”. Losing the badge must not lose the count.
For developers
The bell borrows the item's look but not its full width — it is sized on its own. Letting it inherit width:100% squashed the name beside it to 8px, which no colour or size check would have caught. The dot is positioned inside the bell, so it cannot push the row wider.

Person mark

.tag2

Stands in for someone's picture. Two initials in a circle, used wherever a person is named — the control bar, the foot of the side list, a row in a list of people.

PARLWMDR
Shape
Always a circle — border-radius:50%. A person is a circle and a thing is a rectangle; keeping that split means you can tell at a glance whether a row is about a person or about a record. A square mark reads as a logo or a thumbnail.
Size
28px in a bar or a list row, 36px where it is the main subject. Width and height always equal, so a long name cannot stretch it into an oval.
On a phone
32px minimum, and never the only touch target — the whole row it sits in is the target.
Initials
Two letters, uppercase, from the person's role rather than their name, so the same mark is stable when a name is missing.
Access
Decoration. It is aria-hidden and the person's name sits beside it as real text. Initials alone are never the only way to tell who someone is.
For developers
Set flex:0 0 <size> as well as width and height. Without the flex basis a tight row shrinks it into an ellipse, which no check will report because nothing has overflowed.

Foldable section

details.fold

A part of a page that is worth keeping but not worth reading every time. Housekeeping lists, long records, anything a person needs occasionally and would otherwise have to scroll past.

11 pages

The list sits here, closed until someone asks for it.

Built on
A real <details> and <summary>. Keyboard, screen reader and find-in-page all work without a line of script.
Summary
32px tall minimum, a caret then the label. The label says how much is inside — “11 pages”, not “Show more”, so someone can decide whether to open it.
On a phone
Summary 44px tall, label 15px.
Caret
Rotates 180° over 120ms, the tap movement. A transform, so no layout work. The body itself does not animate — its height is unknown until it is open, and animating an unknown height is how a list of 200 rows drops frames.
Closed by default
Anything folded starts closed, and the page must make sense without opening it. Never fold something a person needs in order to finish the task in front of them.
Wording
No note saying “closed by default” or “click to expand”. The caret already says it. A label that explains the control instead of the content is wasted.
Access
<summary> reports its own expanded state — do not add aria-expanded, and do not put a heading inside it and a second one above it.
For developers
The body may scroll, and .fold__body is on the list of regions allowed to. Anything else that scrolls inside a page is reported by GN.CHECK.scrolls().

The hero number
People affected — a declared figure on the record itself, like its severity level, not computed from linked data. 26px, tabular figures.
The three counts
Organisations, shelters and warehouses attached to this disaster — real, computed relationships, not declared. Zero is a true answer for a disaster just raised: nothing has been tagged to it yet.
Ongoing / Closed only
No archive on this page — a disaster only ever moves between the two, and both stay in the one list. Closing is not itself good or bad news, so the chip is plain neutral either way, never a status colour. Closing and reopening both ask first, worded plainly: “Close Hurricane Marisol? It stays in this list, marked Closed, and can be reopened any time.”
The closed state
Three changes only. Name steps to --text-2, the hero number and the three counts step to --text-3, and a footer line replaces where an open card has nothing yet to say — when it closed, and how long it ran, both computed from real dates via CALC.daysBetween.
The menu
Edit, then Close or Reopen depending on which state the card is in — a short list inside a panel(), not a hand-rolled anchored dropdown. That gets the focus trap, Escape and backdrop dismissal every other panel in this kit already has for free, at the cost of a full-screen veil for what is otherwise a small choice. Worth it the first time this pattern was needed; revisit if a card ever needs four or more actions, where an anchored menu starts pulling its weight.
Who gets a menu at all
Super Admin, on every card — declaring or closing a disaster is a network-wide act. A Relief Org Admin gets one only on a disaster their own org declared: d.addedByOrg === c.person.org. List toolbar

.ask .pick

Search, filters, and a Card/Table switch, for any page that lists more than a handful of records.

View
Search
Filters as you type, no button to press. A search box that needs a submit action makes someone wonder whether the list in front of them is already current.
Filters
Real dropdowns, each with an explicit “All”. Filter values are never a hand-picked shortlist — the Type filter reads from the same list the record's own type picker uses, so a type added there is a real filter option here without new code.
Card / Table
Desktop only. On a phone this switch does not render — cards are the only view, per the rule that a control with nothing to control does not render (see A control with one option is not a control).
No Live/Archived here
Not every list needs the archive tab. The Disasters list only ever shows Ongoing and Closed, both live, both in the one list — archiving would be a different, later act this page does not offer. Whether a list gets an archive tab is a per-page decision, not something this toolbar assumes.
For developers — the one real trap here
.pick is also this design-system page's own Desktop/Phone switch, and that switch is deliberately sized for whoever is driving the kit, not for the simulated phone floor. Reusing .pick inside actual page content — like this toolbar — crosses into the product, and the product's phone floor applies. Missed the first time, caught by GN.A11Y.audit() on Super Admin's own phone surface: two buttons at 12.5px on a 26px target, both under floor. Fixed with a phone-only override scoped to content, leaving the page-chrome use of .pick untouched.
For developers — typing without losing focus
A live-filtering search box redraws the list on every keystroke, and this kit's screens redraw whole rather than diff. Without help, the input node is destroyed and rebuilt each time and loses focus after one character. Any field marked data-keep-focus="…" survives a redraw: its value is already correct because state drives it, and paint() now restores focus and the cursor position to whichever element carries a matching value after every repaint.

Form panel

panel()

Add or edit a record in place, without leaving the list. One form serves both — Edit opens it pre-filled, Add opens it blank — so there is only ever one place to keep a record's fields right.

Add warehouse

This needs a name.

Fields, not a wizard
Panel forms in this kit are unstructured DOM elements read directly at submit — input.value, a howMany() field's own .read(). Nothing in the field's own typing needs to trigger a redraw, because nothing else on screen depends on it until Add or Save is pressed. That is what makes a form panel simpler to build than the search box above: no data-keep-focus needed here, because the panel is never rebuilt out from under itself.
One required field, by design
Every select defaults to a real, valid choice; a number field's own floor keeps it from ever reaching an invalid value. That leaves the name as the only thing that can actually be missing — one validation to get right, rather than five to maintain.
A failed submit
Rebuilds only the one field's label-and-message wrapper — nameWrap.replaceWith(freshWrap) — not the whole panel. The typed value stays exactly as typed, in the same input node, and focus returns to it. aria-invalid is set on the field itself, not only implied by red text.
For developers
Every new record is stamped the same way seed data is — addedBy, addedByOrg, fromCatalogue, plus the full archive family (archived: false and its three companions) — set directly rather than through the internal stamp() helper, which is not exposed outside Store.
For developers — the history line has to be inside the write
Store.note() only ever mutates now.history in memory — nothing about it persists or notifies. Called inside the same Store.change(fn) that mutates the record, the wrapper's own write()+tell() covers both at once. Called standalone after that block instead, the screen still redraws correctly — it reads the same in-memory object either way — which is exactly what hides the mistake until a reload silently drops the history line. Caught here before it shipped; see VERSION_HISTORY.md.

Two-step wizard

steps()

Add a disaster: which type, and where, then who is involved. Two steps in one panel, refreshed in place rather than closed and reopened, so nothing already typed is ever lost moving between them.

  2. 02Who is involved

Comes in automatically: Beaumont depot fleet, Delta Haulage, Luis Obando (volunteer)

One record, two doors, one form
The exact same wizard opens blank from "Add disaster" or pre-filled from a card's Edit. Editing an existing disaster can change everything a new one can — name, type, location, every tag — because there has only ever been one place that knows how to build one.
Type: pick one, or add one
Chips, not a dropdown, because there are usually five or fewer and a glance should be enough. Adding a type writes it into this place's own list for real — Store.s.disasterTypes, not the constant it started from — so it shows up as a genuine option in the Disasters list's Type filter afterward, not just for the rest of this session.
A warehouse's fleet rides along
Tick a warehouse in step 2 and its fleet — and any volunteer based there — appears under "Comes in automatically" before the panel is even submitted. Unticking it removes them just as immediately. Nothing about this needs the whole panel, or even the whole step, rebuilt: only the fleet section's own container is emptied and redrawn, so the warehouse checkboxes above it are never touched by their own side effect.
Automatic and manual never overlap
A fleet or volunteer riding in via a ticked warehouse does not also appear in the manual "add others" list — it would be the same inclusion counted, and offered to be unticked, twice. The moment its warehouse is unticked, it reappears there as a real choice.
What a tick actually writes
Only what was ticked by hand. A fleet included automatically is never written to its own disasters field — the relationship is computed fresh every time from which warehouses are tagged, the same way the Organisations count on a card is computed, not stored twice.
For developers
Every field is read from the live DOM at submit — nothing is mirrored into a parallel state object except where a value has to survive a full step rebuild (name, type, the tag arrays). refresh() replaces the panel's own .panel__mid and .panel__end in place; the panel itself is never closed and reopened between steps, so U.panel()'s focus trap only ever engages once per wizard, not once per step.
08

Patterns

How components go together for the things this product does over and over.

The desktop app fills the window

On a desktop there is no frame around the app, no card, no border, no shadow, and no caption describing it. The app is the window. Every screen reflows to whatever width and height it is given, from a small laptop to a wall display.

  • Nothing carries a fixed width. Panels and lists take the space they are given.
  • Screens react to the app's width, not the window's, so a narrow panel on a wide screen behaves like a narrow screen. Below roughly 760px the side list becomes a sheet reached from a button.
  • Prose keeps a reading width — around 66ch — and stops there. Data surfaces fill. A line of text 200 characters wide is unreadable no matter how much room there is.
  • No caption naming the person, their scope or their place. All three sit in the control bar above, and that is where they are changed. Saying it again on every screen is noise, and two copies drift apart.
One scroller per region

The page itself must never scroll — not sideways, not downward. Exactly one region inside a screen scrolls, and it is the screen body. A second scrollbar appearing inside a page means something has been given a fixed height it did not need, and it costs a person their place on the page. Only a short list of regions may scroll at all; anything else is reported by GN.CHECK.scrolls().

How it is built. The stage, the app and the screen body are a column of flex children, each with min-height:0 so they can be smaller than their content. The screen body is the only one with overflow-y:auto. Leaving out min-height:0 is what makes a long page — the Archived page, for one — stretch the whole app instead of scrolling inside it.

The phone app keeps its frame

A phone is shown inside a device frame with the device name and the scale it is drawn at, because a stakeholder needs to know they are looking at a 412px screen shown small, not a small app. That caption is deliberate, and it is the one place a caption is kept.

  • Standard device sizes, not fluid. The frame is the point.
  • The screen body is still the only scroller; the header and the bottom bar stay put.
  • Four main pages in a bottom bar with 44px targets. Everything else is reached from a sheet.

Ask, then confirm

  1. Person fills in what they need. Nothing is checked while they type.
  2. They press the main button. Everything is checked at once.
  3. Anything wrong: the count is spoken, each field shows its own problem, focus stays where it is.
  4. Nothing wrong: button shows a spinner and says what it is doing.
  5. Worked: brief message, and the screen moves on.
  6. Failed: message in place with a way out. Whatever they typed is still there.
The rule that matters

A failure must never lose what someone typed. Under pressure, retyping is how a task gets abandoned.

List, then detail

  • The list shows only what is needed to choose: name, status, when it is needed by, how much.
  • Opening a row keeps the list position, so going back does not lose the place.
  • On a phone the detail is a full screen with a back arrow, not a panel — panels are too small for the amount of detail here.
  • On desktop the detail replaces the page and the breadcrumb shows the way back.

Several steps

  • Four steps at most. More than that, split the task.
  • Each step stands alone and can be returned to.
  • The last step shows everything back before it is sent.
  • Leaving part-way keeps a draft. It is never silently thrown away.

Working offline

A driver loses signal constantly. The rule: never block on the network.

  • The action is accepted, marked as waiting, and sent when signal returns.
  • The person is told plainly it is waiting, and how many things are waiting.
  • Nothing about it looks like a failure, because it is not one.
  • When it sends, a brief message confirms it. If it then fails, that is a real failure and gets a message in place.

Nothing is ever deleted

There is no delete anywhere in this product. Removing something archives it, and the Archived page brings it back.

  • Every record carries who archived it, when, and why. The reason is asked for, not optional.
  • Lists show live records only. The Archived page shows the rest.
  • Bringing something back is written into what happened, the same as archiving it.
  • Whole people-views can go out of sight too, and come back the same way. They are listed with a reason and a date.
  • A page that no side list points at is registered, not orphaned — otherwise it is lost without anyone deciding to lose it.
Why it is worth the trouble

In a disaster, someone will archive the wrong warehouse at two in the morning. The cost of a wrong delete is unrecoverable work; the cost of a wrong archive is one click.

Handing over between people

The point of the whole product: one person's action becomes another person's job. Every handover follows the same shape.

  1. The action changes something both people can see.
  2. The other person gets a message — on the phone if it needs acting on now, in the app if not.
  3. The record of what happened is written and cannot be edited.
  4. The sender can see it was received. Silence is never the confirmation.

A control with one option is not a control

The Place switcher and the language switcher both follow this. The prototype started with two places (UAE, US) and two languages per place, so a picker made sense. Scoped to one place and one language, a picker showing a single always-pressed button teaches nothing and clicks nowhere — it is furniture pretending to be a control.

  • Below two live options, the group returns nothing rather than a single disabled button. This is the same call already made for the frame caption: something with only one value does not need a widget to display it.
  • "Live" is counted the same reversible way as a hidden person or page — see Nothing is ever deleted above. Hiding UAE or a language does not touch its data or its code; it changes only what the control bar offers. Bringing UAE back makes the Place group reappear on its own, the moment it is restored — no reload, no second step.
  • The two kinds of hide are independent on purpose. Restoring a place does not restore a language, and the reverse. Someone could want the US shown in Spanish without UAE, or UAE back without Arabic.

When things go wrong

Seven failures, each one demonstrable on demand in the prototype, each with a written way out. This is the part of the design that gets least attention and matters most.

NameWhat happenedWhat the person seesThe way out
MISSINGSomething was not filled inEach field shows its own problem; the count is spokenFix and send again. Nothing was sent, nothing was lost.
TAKENSomeone else set that stock aside firstMessage in place naming what went and how much is leftSend what is left, or pick another warehouse. Both offered as buttons.
SHORTNot enough stock to cover the requestExact numbers: what is here, what is needed, the gap, and when more arrivesSend part now and the rest later, or ask another warehouse.
DROPPEDConnection went before it savedMessage in place saying nothing was changedTry again. Everything typed is still on screen.
OFFLINENo signal at allTold it is saved on the phone and will send itselfNothing to do. It sends when signal returns.
BARREDThis person is not allowed to do thatPlain statement, and who can do itHand it to the named person. Never a dead end.
STALEThe screen is out of dateWhat changed underneath, and by whomReload and see the new state before saving.
Do

Name the thing. “Not enough baby formula — 60 here, 240 needed” beats “insufficient stock”.

Do not

Blame the person. “That did not save” not “you failed to save”.

Do

Say what was not changed. Under pressure, the first question is always “did it half-work?”

Do not

Offer a retry that will fail the same way. If it cannot work, say what will.

  • Keyboard only, start to finish, on every flow.

Two grey values failing contrast on tinted backgrounds. An icon-only button 33px wide against a 44px rule. A progress bar animating its width, and later the side list animating its own. Who a change affects

Every change is meant to be checked across everyone who uses the product. Remembering to do that does not scale, so it is worked out instead.

QuestionAsk it
If I change how warehouses work, who and what does that touch?GN.IMPACT.of('stores')
If I change this page, what does it read and who sees it?GN.IMPACT.ofPage('disasters')
Show me everything at onceGN.IMPACT.all()

The answer names the people in use, the pages, whether a phone is involved, and — importantly — the people currently out of sight who would also be affected when they come back. That last part is the one a person doing this from memory always misses.

It works because each record kind declares which pages read it, in one place. Add a page that reads a kind, add it to that list in the same pass. The link check fails if a side list points at nothing.

The rules a build must keep

  1. No figure typed into a screen. Every number comes from the arithmetic layer. There is a check for it.
  2. No unit typed into a screen. Units come from the place layer.
  3. Values stored metric, converted only when shown.
  4. Status codes stored, words shown. Never print a raw code.
  5. Nouns come from the word list, so a new place needs no screen changes.
  6. Only fading and moving. Nothing that costs layout work.
  7. Nothing blocks on the network in the phone app.

Adding a place

One entry in the place list, one optional entry in the word list. Record identifiers are deliberately identical across places, so screens read identifiers and the place supplies the content. No screen mentions a place by name and none ever should.
